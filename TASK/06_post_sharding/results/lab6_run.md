# Lab 6 — фактические проверки после шардирования `adoptions`

Дата: 2026-09-17 00:19. Данные: 100 000 записей adoptions в БД shelter_shard на трёх шардах.

## 2. Single-shard query: GET /api/users/{id}/adoptions

Router: hash32(42) % 3 = 1 -> запрос идёт только на shard1.
SQL на shard1: `SELECT ... FROM adoptions WHERE user_id = 42` -> 27 строк (id 1337..99986).
Другие шарды НЕ опрашиваются: запись не может находиться где-то ещё —
роутер детерминирован. Это самый дешёвый класс запросов после шардирования.

## 3. Агрегация: GET /api/adoptions/stats/by-status

| Шард | Pending | Approved | Completed | Rejected | Всего |
|------|--------:|---------:|----------:|---------:|------:|
| shard0 | 8 430 | 8 500 | 8 423 | 8 449 | 33 802 |
| shard1 | 8 345 | 8 314 | 8 480 | 8 453 | 33 592 |
| shard2 | 8 169 | 8 101 | 8 160 | 8 176 | 32 606 |
| **merge (sum)** | **24 944** | **24 915** | **25 063** | **25 078** | **100 000** |

На одном шарде запрос выполнить нельзя: каждый шард видит только свою часть.
Результаты объединяются в backend (merge): COUNT/SUM складываются, AVG — нет
(нужны sum и count с каждого шарда, среднее — после merge). Время = max(шард)
+ merge; запросы к шардам идут параллельно, но с ростом N растёт merge-работа.

## 4. JOIN между шардами: adoptions (шард) + animals (Primary)

GetDetailedByUserIdAsync (JOIN adoptions+animals+users+shelters) обычным SQL
выполнить нельзя: заявки лежат на шарде, справочники — на Primary.
Практический паттерн — два запроса и merge в приложении:
1) шарде shard1: заявки пользователя -> 5 строк, animal_id = [18, 354, 261, 261, 43]
2) Primary: SELECT id, name FROM animals WHERE id IN (18, 43, 261, 354)
3) merge в приложении: собираем DTO на стороне backend, например:
   - Animal #18 (animal_id=18): заявка на shard1, справочник на Primary
   - Animal #354 (animal_id=354): заявка на shard1, справочник на Primary
   - Animal #261 (animal_id=261): заявка на shard1, справочник на Primary
   - Animal #261 (animal_id=261): заявка на shard1, справочник на Primary
   - Animal #43 (animal_id=43): заявка на shard1, справочник на Primary

Между шардами пришлось бы передавать либо все заявки пользователя, либо
все животные — таблицы не могут встретиться в одном SQL-движке.
Co-location: шардируем animals по тому же ключу — тогда JOIN заявки+животное
чаще выполняется внутри одного шарда.

## 5. ORDER BY + LIMIT: топ заявок (аналог GET /api/animals с сортировкой)

shard0: top 10 по created_at DESC, самая старая в выборке = 2026-09-17 09:49:00
shard1: top 10 по created_at DESC, самая старая в выборке = 2026-09-17 04:16:00
shard2: top 10 по created_at DESC, самая старая в выборке = 2026-09-17 06:58:00

Merge -> глобальный top 10 (первые 3):
   id=30 965 user_id=3316 created_at=2026-09-17 11:54:00
   id=75 840 user_id=1841 created_at=2026-09-17 11:44:00
   id=67 834 user_id=3085 created_at=2026-09-17 11:30:00

Брать LIMIT 10 только с одного шарда нельзя: его самые свежие записи могут
оказаться старше свежих записей других шардов. Merge требует top-10 с КАЖДОГО
шарда; при LIMIT < 10 на шарде глобальный top может оказаться неполным.
Чем глубже пагинация, тем дороже merge (OFFSET в распределённом виде дорог).

## 6. Отказ одного шарда (docker stop shelter_shard2)

- shard2: недоступен — connection to server at "localhost" (::1), port 5447 failed: could not receive data from server: Software caused connection abort (0x00002745/10053)
- shard0: запросы работают (33 802 строк).

Недоступны: все adoptions пользователей, маршрутизируемых на shard 2
(~1/3 данных). Перестают работать их endpoint'ы (GET/POST/PUT заявок)
и глобальные агрегаты (COUNT неполон). Остальное (шард 0, 1, справочники
Primary, чтение животных) продолжает работать. Backend обязан: таймауты,
понятная ошибка 503, частичная деградация, ретраи только чтений, healthcheck.
Отказоустойчивость: реплика каждого шарда + failover, бэкапы per-shard,
буферизация записей (outbox) на время недоступности.
- shelter_shard2 запущен обратно и отвечает.

## 7. Hot shard: строки равны, нагрузка — нет

| Шард | Строк | Доля строк | Запросов (модель) | Доля запросов |
|------|------:|-----------:|------------------:|--------------:|
| shard0 | 33 802 | 33.80% | 333 802 | 33.38% |
| shard1 | 33 592 | 33.59% | 633 592 | 63.36% |
| shard2 | 32 606 | 32.61% | 32 606 | 3.26% |

Модель: по одному чтению ленты на запись + «киты» user_id 7/42/1337 (по 300k
опросов своего профиля). Причины перекоса: популярные ключи, тип запросов,
неудачный ключ. Равные строки НЕ означают равную нагрузку. Лечение: кэш
горячих ключей (Redis уже в стеке), ребалансировка дуг, реплика горячего
шарда, составной shard key.
