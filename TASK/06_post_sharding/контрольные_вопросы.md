# Контрольные вопросы и ответы — Лаба 6
## Что происходит с backend-сервисом после шардирования

1. **Чем single-shard query отличается от distributed query?**  
   Single-shard — запрос с условием по shard key (`WHERE user_id = ?`): роутер
   отправляет его ровно в один экземпляр. Distributed — без ключа или с
   агрегацией по всем данным: нужно опросить все шарды и объединить результаты.

2. **Почему JOIN между шардами сложнее обычного JOIN?**  
   JOIN выполняет один SQL-движок; связанные строки лежат на разных экземплярах,
   а межсерверного JOIN в PostgreSQL нет. Приходится делать несколько запросов и
   объединять данные в приложении (или в спец. слое-координаторе), что дороже и
   без транзакционной целостности.

3. **Как выполнить COUNT(*) по всем шардам?**  
   `COUNT(*)` на каждом шарде параллельно, затем сложить числа в backend.
   Для GROUP BY — выполнить группировку на каждом шарде и просуммировать
   одинаковые группы.

4. **Почему ORDER BY ... LIMIT требует объединения результатов?**  
   Глобальный топ-N — это объединение топ-N каждого шарда: нужные строки могут
   быть на любом из них. LIMIT только с одного шарда даёт неполный/неверный
   ответ (проверено: топ-3 прогона пришёл с разных шардов).

5. **Что произойдёт при отказе одного шарда?**  
   Его часть данных (~1/3 в нашем эксперименте) недоступна: падают endpoint'ы
   этих пользователей и глобальные агрегаты. Остальные шарды и справочники
   Primary продолжают работать. Backend должен возвращать 503/деградировать,
   а не падать целиком.

6. **Что такое hot shard?**  
   Шард, принимающий непропорционально большую нагрузку. В модели: строки 33/34/33%,
   а запросы — 33/63/3% из-за «китов». Причины: популярные ключи, тип запросов,
   неудачный shard key.

7. **Почему выбор shard key влияет на JOIN?**  
   Если связанные таблицы шардируются по одному ключу (co-location), их строки
   попадают на один шард и JOIN остаётся локальным. Разные ключи делают JOIN
   распределённым. Для `adoptions`+`animals` co-location по пользователю
   помогает не всегда (животное может принадлежать другому пользователю).

8. **Какие операции особенно плохо подходят для распределённых данных?**  
   Кросс-шардовые JOIN, глобальные уникальные ограничения и последовательности,
   транзакции, затрагивающие несколько шардов (нужен 2PC), глубокая пагинация с
   OFFSET, изменение shard key у существующей записи (физический переезд строки).

9. **Что произойдёт при изменении количества шардов?**  
   Перераспределение данных (лаба 5): modulo — ~76% строк, кольцо — ~28%.
   На время миграции возможны двойные чтения/записи — нужен протокол переноса
   (копия → сверка → переключение роутера).

10. **Чем шардирование отличается от репликации?**  
    Репликация — полные копии одних и тех же данных (масштабирует чтения,
    отказоустойчивость; лаба 4). Шардирование — разные части данных на разных
    узлах (масштабирует объём и запись). Они не исключают друг друга: каждый
    шард может иметь свою реплику.

11. **Может ли шардирование сделать отдельный SQL-запрос быстрее?**  
    Single-shard запрос по ключу — да: меньше таблица (1/3 объёма), локальный
    индекс, меньше конкуренция. Distributed-запросы — нет: они дороже, чем на
    одной машине (merge в приложении, сетевые round-trip'ы).
