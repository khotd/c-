# Контрольные вопросы — Лабораторная работа №3
## Партиционирование PostgreSQL

1. **Что такое partitioning?**  
   Разделение одной логической таблицы на несколько физических частей (партиций) по ключу, при сохранении единого имени таблицы для приложения.

2. **Чем partitioning отличается от индекса?**  
   Индекс ускоряет поиск строк внутри таблицы/партиции. Партиционирование уменьшает объём данных, которые нужно рассматривать (prune), и упрощает lifecycle (drop старых данных). Решают разные проблемы.

3. **Какие стратегии поддерживает PostgreSQL?**  
   RANGE, LIST, HASH (declarative partitioning).

4. **Когда использовать RANGE?**  
   Когда данные естественно делятся по диапазону (даты, числовые интервалы) и запросы часто фильтруют по этому диапазону / нужно удалять старые периоды.

5. **Когда использовать LIST?**  
   Когда есть конечный набор категорий (тип клиента, страна, статус) и запросы часто фильтруют по категории.

6. **Когда использовать HASH?**  
   Когда нужно равномерно распределить нагрузку/данные без естественного диапазона (например, по `user_id`).

7. **Как выбрать partition key?**  
   По полю, которое часто в WHERE, по которому данные растут/архивируются, с достаточной кардинальностью сегментов. Ключ должен попадать в PK/UNIQUE.

8. **Что такое partition pruning?**  
   Исключение ненужных партиций из плана, если условие запроса позволяет понять, какие сегменты не нужны.

9. **Почему pruning может не сработать?**  
   Фильтр не по ключу партиционирования, нестабильное выражение, параметр мешает константному pruning, функция от ключа.

10. **Можно ли использовать индексы вместе с partitioning?**  
    Да. Индекс создаётся на parent и локально на партициях; pruning + index часто лучше, чем одно из двух.

11. **Что будет, если подходящей партиции нет?**  
    INSERT упадёт с ошибкой (если нет DEFAULT). Поэтому будущие партиции создают заранее.

12. **Зачем создавать будущие партиции заранее?**  
    Чтобы ночные/дневные INSERT не ломались, когда наступает новая дата/период.

13. **Почему создание партиций должно быть автоматизировано?**  
    Ручное создание забывается; job идемпотентно поддерживает горизонт.

14. **Чем логирование ошибки отличается от alerting?**  
    Лог можно не заметить. Alert активно уведомляет (email/файл/мессенджер).

15. **Что такое recovery alert?**  
    Уведомление о том, что проблема устранена (переход CRITICAL → OK).

16. **Почему нельзя бесконечно слать одинаковый alert?**  
    Алерт-шторм; нужна дедупликация до смены статуса / recovery.

17. **Всегда ли partitioning ускоряет запросы?**  
    Нет. Запросы без фильтра по ключу обходят все партиции; слишком мелкие/крупные партиции тоже вредят.

18. **Проблемы при неправильном размере партиций?**  
    Слишком мелкие — overhead планирования/метаданных; слишком крупные — слабый prune и тяжёлое обслуживание.

## Ответы на задания стратегии (часть 7)

| Сценарий | Стратегия | Почему |
|----------|-----------|--------|
| A события + удаление старше 3 лет | **RANGE по дате** | Удаление = DROP PARTITION |
| B B2C/B2B/Enterprise | **LIST** | Фильтр по категории |
| C равномерно по user_id | **HASH** | Равномерное распределение |
| D аналитика по created_at BETWEEN | **RANGE по дате** | Pruning по диапазону |
| E платежи по странам EE/LV/LT/... | **LIST** | Дискретные значения стран |

## Границы RANGE

- `created_at = '2026-09-10 12:00:00'` → `events_2026_09_10`  
- `created_at = '2026-09-11 00:00:00'` → `events_2026_09_11` (TO не включает нижнюю границу следующей)  
- Вставка за `2026-09-12` без партиции/DEFAULT → ошибка  
- `TO ('2026-09-11')` — полуинтервал `[FROM, TO)`
