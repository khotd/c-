# Контрольные вопросы и ответы — Лаба 4
## Read Scaling: Primary + Replica

1. **Чем Primary отличается от Replica?**  
   **Primary** — основной экземпляр: принимает чтение и запись (INSERT/UPDATE/DELETE).  
   **Replica** — копия Primary: обычно только чтение (hot standby), получает изменения по репликации.

2. **Почему запись выполняем на Primary?**  
   Только Primary является источником истины для изменений. Replica воспроизводит чужой WAL и в режиме standby запрещает локальную запись — иначе появились бы расхождения копий.

3. **Как изменение из Primary попадает на Replica?**  
   Primary пишет изменение в данные и в **WAL** → по streaming replication WAL передаётся на Replica → Replica применяет (replay) записи WAL у себя.

4. **Что такое WAL в контексте репликации?**  
   Write-Ahead Log — журнал опережающей записи. Сначала фиксируется описание изменения, потом данные. Реплика читает этот поток и повторяет те же изменения.

5. **Что такое replication lag?**  
   Задержка между моментом, когда изменение уже есть на Primary, и моментом, когда оно применено на Replica. Измеряется временем/байтами отставания replay.

6. **Почему следующий SELECT после INSERT потенциально может увидеть старые данные на Replica?**  
   Из‑за replication lag: INSERT уже закоммичен на Primary, а Replica ещё не успела получить/применить WAL. Поэтому read-your-writes на async Replica не гарантируется.

7. **Что именно масштабируется при Read Scaling: скорость одного SQL или способность обслуживать больше чтений?**  
   В первую очередь **пропускная способность системы по чтениям** (больше одновременных SELECT, разгрузка Primary). Один конкретный SQL на Replica не обязан стать быстрее, чем на Primary.

8. **Почему наличие Replica не отменяет необходимость индексов и оптимизации SQL?**  
   Replica выполняет те же планы запросов по своим данным. Медленный Seq Scan останется медленным и на копии. Индексы, партиции и хороший SQL по-прежнему нужны.

9. **Расскажите про CAP-теорему**  
   В распределённой системе из трёх свойств — **Consistency** (согласованность), **Availability** (доступность), **Partition tolerance** (устойчивость к разрыву сети) — при сетевом разделении нельзя одновременно гарантировать все три в сильной форме.  
   Async Primary+Replica обычно выбирает доступность чтения с **ослабленной consistency** (возможен lag). Синхронная репликация усиливает согласованность, но может снизить доступность записи при проблемах с Replica.
