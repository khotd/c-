# Контрольные вопросы — Лабораторная работа №2
## Когда индексов недостаточно

1. **Почему Seq Scan не всегда плохой план?**  
   Если запрос читает большую долю таблицы, последовательное чтение дешевле множества случайных обращений по индексу.

2. **Почему PostgreSQL может не использовать существующий индекс?**  
   Низкая селективность, устаревшая статистика, несовпадение выражения, высокий cost Index Scan, неверный префикс составного индекса.

3. **Что происходит с индексом при INSERT?**  
   Для каждой новой строки ключ добавляется в структуру индекса (B-Tree и др.) — дополнительный I/O и CPU.

4. **Почему много индексов замедляет запись?**  
   Каждый INSERT/UPDATE/DELETE обновляет все затронутые индексы.

5. **Что такое селективность?**  
   Доля строк, удовлетворяющих условию фильтрации.

6. **Почему индекс хорош для небольшой части таблицы?**  
   Мало обращений к heap через TID, выигрыш против полного скана.

7. **Почему индекс менее полезен, если возвращается большая часть таблицы?**  
   Random I/O по куче дороже Seq Scan.

8. **Зачем нужен EXPLAIN ANALYZE?**  
   Чтобы увидеть реальный план и время, а не только оценку планировщика.

9. **Что значит Rows Removed by Filter?**  
   Сколько строк просмотрели и отбросили фильтром после доступа (часто после Seq/Index Scan).

10. **Что значит Index Cond?**  
    Условие, применённое самим индексом (поиск по ключу), а не Filter после чтения.

11. **Чем Index Scan отличается от Bitmap Index Scan?**  
    Index Scan читает строки по одной (часто по TID сразу). Bitmap сначала собирает bitmap TID’ов, затем читает heap пачками.

12. **Почему важен порядок колонок в составном индексе?**  
    Работает leftmost prefix: `(user_id, created_at)` помогает по `user_id`, но не по одному `created_at`.

13. **Почему GROUP BY может оставаться дорогим при индексе?**  
    Нужно агрегировать много строк; индекс может сузить диапазон, но не убрать группировку большого объёма.

14. **Как статистика влияет на план?**  
    Планировщик оценивает rows/cost по pg_statistic; устаревшая статистика → плохой план. Помогает `ANALYZE`.

15. **Что происходит с производительностью при росте таблицы?**  
    Seq Scan линейно дорожает; даже Index Scan может замедляться из‑за высоты B-Tree, размера индексов и I/O; агрегации и широкие диапазоны страдают сильнее.

16. **Почему нельзя индексировать все колонки?**  
    Место на диске + цена записи + maintenance; часть индексов не окупится.

17. **Как узнать размер таблицы?**  
    `pg_size_pretty(pg_relation_size('table'))` и `pg_total_relation_size('table')` (с индексами).

18. **Как узнать размер индекса?**  
    `pg_size_pretty(pg_relation_size(indexrelid))` из `pg_stat_user_indexes` / `pg_relation_size('index_name')`.

## Вывод по границе применимости индексов (на измерениях)

### Part A — `events` (`WHERE user_id = 123`)

| Объём | Без индекса | С индексом |
|-------|-------------|------------|
| 100k | 6.3 ms | 0.15 ms |
| 1M | 31.4 ms | 0.19 ms |
| 5M | 160.8 ms | 0.36 ms |

INSERT 100k: 284 ms без индексов → **830 ms** с тремя индексами.

### Part B — `adoptions` / `adoptions_growth`

Узкое место — range по `created_at` (30 дней): на 5M **~484 ms** без индекса / **~98 ms** с индексом.  
`user_id + LIMIT 50` с composite остаётся **~0.1 ms**.

**Формулировка:** при объёме около **5 млн** записей запрос диапазона дат начинает занимать порядка **0.1–0.5 с**; индекс снижает время, но дальнейший рост снова упрётся в объём читаемых данных — одного индекса недостаточно, нужен partitioning (лаба 3).
