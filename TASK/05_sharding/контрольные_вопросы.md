# Контрольные вопросы и ответы — Лаба 5
## Шардирование: Router и Consistent Hashing

1. **Что такое shard?**  
   Отдельный экземпляр PostgreSQL, хранящий свою часть данных сущности. В лабе —
   `shelter_shard0/1/2` (:5445–5447), каждый со своей БД `shelter_shard`.

2. **Что такое shard key?**  
   Поле, по которому вычисляется расположение записи. Для `adoptions` это
   **`user_id`**: известен до INSERT, все заявки пользователя лежат вместе.

3. **Почему нельзя просто случайно распределять записи между PostgreSQL?**  
   Запись нельзя будет найти: для чтения нужно знать, где она. Случайное
   распределение потребовало бы опроса всех шардов на каждый запрос.

4. **Как работает hash(key) % N?**  
   `hash32(user_id) = ('x' || substr(md5(user_id::text),1,8))::bit(32)::bigint`,
   затем `shard = hash32 % N`. Детерминированно, равномерно, без состояния.

5. **Почему изменение количества шардов является проблемой?**  
   Меняется делитель → меняется остаток почти для всех ключей. Фактически:
   при 3→4 переезжает **76.01%** (76 012 из 100 000) записей.

6. **Что такое Consistent Hash Ring?**  
   Кольцо 0..2^64: шарды и ключи отображаются хешем в точки кольца; запись
   принадлежит ближайшему шарду по часовой стрелке. При изменении числа узлов
   двигаются только дуги между старой и новой точками.

7. **Почему при добавлении шарда не приходится переносить все данные?**  
   Позиции vnode-точек существующих шардов не меняются (имя точки зависит только
   от индекса шарда), новый узел перехватывает лишь свою дугу: **27.81%** против
   76.01% у modulo.

8. **Что такое virtual nodes и зачем они нужны?**  
   Несколько (у нас 100) точек кольца на шард. Сглаживают разброс размеров дуг:
   с 1 vnode max/min = 9.46, с 10 — 2.21, со 100 — 1.14.

9. **Может ли Consistent Hashing гарантировать идеальное распределение нагрузки?**  
   Нет. Оно статистическое: ключи не обязаны распределяться поровну между дугами,
   а «горячий» пользователь всё равно целиком живёт на одном шарде.

10. **Что произойдёт, если один шард станет значительно более загруженным остальных?**  
    Он станет узким местом (латентность, очередь соединений). Лечится переносом
    части vnode-дуг/ключей на другие узлы, репликой «горячего» шарда или
    составным shard key.

# Контрольные ответы (дубль для отчёта) — Лаба 5

1. **Shard** — независимый экземпляр PostgreSQL с частью данных сервиса.
2. **Shard key** (`user_id`) определяет, на какой шард попадёт запись.
3. Случайное распределение не позволяет найти запись при чтении.
4. `hash(key) % N` даёт номер шарда детерминированно и равномерно.
5. Смена N меняет остаток почти для всех ключей → массовый переезд данных.
6. Hash ring: узлы и ключи на кольце, запись берёт ближайший узел по часовой.
7. Кольцо сохраняет старые точки — переезжает только дуга нового узла.
8. Virtual nodes размножают точки узла, выравнивая дуги (9.46 → 1.14 при 100).
9. Нет, распределение статистическое; горячий ключ не делится.
10. Перегруженный шард тормозит свои запросы; нужен ребалансинг/реплика.
