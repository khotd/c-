# Лабораторная работа №5
# Шардирование PostgreSQL: Router и Consistent Hashing

Проект: Animal Shelter (`project/`).  
Сырые результаты: `TASK/05_sharding/results/`.

**Цель:** распределить данные сущности `adoptions` между тремя независимыми
PostgreSQL, сравнить стратегии `hash(key) % N` и Consistent Hashing по объёму
перемещения данных при изменении числа шардов.

---

## Часть 1. Выбор данных для шардирования

| Вопрос | Ответ |
|--------|-------|
| Сущность | **`adoptions`** — заявки на усыновление (основная растущая сущность сервиса, см. `project/README.md`) |
| Shard key | **`user_id`** |
| Почему | известен **до** INSERT (заявка создаётся пользователем); все заявки пользователя лежат вместе — `GET /api/users/{id}/adoptions` становится single-shard; user_id не меняется UPDATE'ами |
| Равномерность | user_id равномерен по аудитории → хеш даст равномерное распределение; перекос возможен от «китов» (пользователи с тысячами заявок) |
| Запросы с этим ключом | `GET /api/users/{userId}/adoptions`, `GET /api/animals/{animalId}/adoptions` (частично), INSERT/UPDATE/DELETE заявки |

## Часть 3. Router внутри сервиса

`TASK/05_sharding/scripts/shard_router.py` — две стратегии:

```python
# Стратегия A: shard = hash(shard_key) % N
hash32(key) = int(md5(str(key))[:8], 16)      # 0 .. 2^32-1
shard = hash32(user_id) % N

# Стратегия B: Consistent Hash Ring
hash64(key)  — 64-битный хеш ключа (позиция на кольце)
точки узлов: hash64("shard-{S}-vnode-{V}"), V = 1..100 (virtual nodes)
запись -> ближайшая точка кольца по часовой стрелке (бинарный поиск)
```

Роутер возвращает номер экземпляра, после чего backend берёт соответствующую
connection string (по образцу лабы 4, где `GET /api/animals` читает с
`ReplicaConnection`). Те же хеши реализованы в SQL —
`TASK/05_sharding/sql/02_router_functions.sql`:

| user_id | hash32(user_id) | mod 3 → шард |
|--------:|----------------:|--------------|
| 101 | 951 316 472 | Shard 2 |
| 102 | 3 968 423 523 | Shard 0 |
| 103 | 1 769 262 682 | Shard 1 |

MD5 здесь — только стабильный детерминированный хеш для распределения.

## Часть 4. Распределение 100 000 записей

Сгенерированы записи `adoptions` (user_id ∈ 1..5000, animal_id ∈ 1..1000,
4 статуса, даты за ~700 дней) и **физически загружены** в шарды обеими
стратегиями (скрипт `scripts/lab5_sharding.py`, лог `results/lab5_run.md`).

### hash(user_id) % N

| Шард | Записей | Доля |
|------|--------:|-----:|
| shard0 | 33 802 | 33.80% |
| shard1 | 33 592 | 33.59% |
| shard2 | 32 606 | 32.61% |

Распределение **близко к равномерному** (max/min = 1.037) — заметного дисбаланса
нет. Малый перекос (~1200 записей) — норма хеш-распределения; при равных узлах
он безвреден, но «горячий» пользователь целиком попадает на один шард.

### Consistent Hashing (100 vnodes)

| Шард | Записей | Доля |
|------|--------:|-----:|
| shard0 | 31 359 | 31.36% |
| shard1 | 35 692 | 35.69% |
| shard2 | 32 949 | 32.95% |

max/min = 1.138 — приемлемо; именно vnode'ы уменьшают разброс (см. Часть 6).

## Часть 5. Что произойдёт при 3 → 4 шарда (hash % N)

Для каждой из 100 000 записей сравнено `hash32 % 3` и `hash32 % 4`:

| Метрика | Значение |
|---------|---------:|
| Всего записей | 100 000 |
| Изменили шард | **76 012** |
| Остались на прежнем шарде | 23 988 |
| **Процент перемещаемых** | **76.01%** |

**Почему так много:** при смене делителя меняется остаток почти для всех ключей.
Ключ сохраняет остаток только если `hash32(key)` даёт одинаковые остатки по
модулям 3 и 4 — вероятность ≈ 25%, что и наблюдается (23.99%).

## Часть 6. Consistent Hashing и сравнение стратегий

Кольцо реализовано в `shard_router.py` (100 vnodes, бинарный поиск, замыкание
кольца). Тот же набор записей распределён кольцом в БД `shelter_ring`, после
чего повторён расчёт 3 → 4 (появляется узел `shard-3-vnode-*`):

| Стратегия | Перемещено | Из 100 000 | Процент |
|-----------|-----------:|-----------:|--------:|
| hash(key) % N | 76 012 | 100 000 | **76.01%** |
| Consistent Hashing | 27 806 | 100 000 | **27.81%** |

**Почему результаты отличаются:** кольцо сохраняет позиции уже существующих
узлов — новый узел перехватывает только ключи своей дуги (~1/N пространства).
Modulo перемешивает всё ключевое пространство заново.

**Влияние vnodes** (распределение 100 000 записей по 3 шардам):

| vnodes | shard0 / shard1 / shard2 | max/min |
|-------:|--------------------------|--------:|
| 1 | 7 548 / 21 029 / 71 423 | 9.463 |
| 10 | 19 561 / 37 245 / 43 194 | 2.208 |
| 100 | 31 359 / 35 692 / 32 949 | 1.138 |

**Ещё один шард (4 → 5):** кольцом снова переедет ≈ 1/5 пространства ключей
(~20%), modulo — ≈ 80%. **Удаление шарда:** кольцо отдаёт дуги удалённого узла
соседям (у нас 27.81% записей); modulo снова перемешивает почти всё.

## Часть 8. Итог

**Shard** — отдельный экземпляр PostgreSQL, хранящий свою часть данных сервиса.
**Shard key** (`user_id` для `adoptions`) — поле, детерминированно определяющее
расположение записи. **Router** нужен, чтобы по ключу выбрать экземпляр для
чтения/записи без опроса всех узлов. **hash(key) % N** прост и равномерен, но
при смене N меняет остаток почти для всех ключей — у нас переезжало **76%**
данных. **Consistent Hashing** помещает узлы и ключи на кольцо: новый узел
забирает только свою дугу — **27.8%** перемещений, и virtual nodes выравнивают
дуги (9.46 → 1.14). Для своего сервиса я бы выбрал кольцо по `user_id`
с vnode'ами, репликами каждого шарда и заранее описанной процедурой переноса
дуг, потому что сервис будет расти по числу пользователей, а простой на
перемещение 76% данных недопустим.
