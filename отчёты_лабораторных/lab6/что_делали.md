# Лаба 6 — что мы делали

**Тема:** поведение backend-сервиса после шардирования — single-shard против
distributed запросов, JOIN, агрегации, отказ шарда, hot shard.

### Коротко
1. Проанализировали **реальные запросы сервиса** (`AnimalRepository`,
   `AdoptionRepository`) после шардирования `adoptions` по `user_id`.
2. Показали **single-shard** запрос: `WHERE user_id = ?` идёт ровно на один
   шард (27 строк на shard1, остальные шарды не опрашивались).
3. Выполнили **распределённую агрегацию** `COUNT GROUP BY status`: по шардам +
   merge в backend (итого ровно 100 000).
4. Разобрали **JOIN** заявки со справочниками Primary: два запроса + merge,
   обычный SQL невозможен; обсудили co-location.
5. Показали **ORDER BY + LIMIT**: топ-10 с каждого шарда + merge, и почему
   LIMIT с одного шарда даёт неверный ответ.
6. Живой тест **отказа**: `docker stop shelter_shard2` → данные недоступны,
   остальные шарды работают; контейнер возвращён в healthy.
7. Смоделировали **hot shard**: строки 33/34/33%, нагрузка 33/63/3% из-за «китов».
8. Итоговый **анализ shard key**: `user_id` подходит, с оговорками по
   JOIN/агрегациям/балансировке.
