# Лабораторная работа №6
# Что происходит с backend-сервисом после шардирования

Проект: Animal Shelter (`project/`).  
Сырые результаты: `TASK/06_post_sharding/results/lab6_run.md`.

**Цель:** проанализировать реальные запросы сервиса и определить, какие
выполняются на одном шарде, а какие требуют обращения к нескольким.
Стенд — шарды лабы 5 (100 000 записей `adoptions`, shard key `user_id`).

---

## Часть 2. Single-Shard Query

Реальный запрос сервиса — `AdoptionRepository.GetByUserIdAsync`
(`GET /api/users/{userId}/adoptions`):

```sql
SELECT * FROM adoptions
WHERE user_id = @UserId
ORDER BY created_at DESC;
```

Фактический прогон (user_id = 42):

```text
Router: hash32(42) % 3 = 1  ->  запрос идёт только на shard1
SELECT ... WHERE user_id = 42  ->  27 строк
```

**Почему не нужны другие шарды:** роутер детерминирован — запись с
`user_id = 42` физически не может находиться в другом экземпляре. Локальный
индекс `(user_id)` сохранён на шарде. Это самый дешёвый класс запросов:
один сетевой узел, 1/3 таблицы.

## Часть 3. Агрегирующий запрос

Реальный запрос — `AdoptionRepository.GetStatsByStatusAsync`
(`GET /api/adoptions/stats/by-status`, `COUNT(*) GROUP BY status`).
Фактические результаты прогонов по шардам и merge в backend:

| Шард | Pending | Approved | Completed | Rejected | Всего |
|------|--------:|---------:|----------:|---------:|------:|
| shard0 | 8 430 | 8 500 | 8 423 | 8 449 | 33 802 |
| shard1 | 8 345 | 8 314 | 8 480 | 8 453 | 33 592 |
| shard2 | 8 169 | 8 101 | 8 160 | 8 176 | 32 606 |
| **merge (sum)** | **24 944** | **24 915** | **25 063** | **25 078** | **100 000** |

Ответы:
1. **Только на одном шарде — нельзя:** каждый шард видит лишь свою часть.
2. **Результаты объединяются в backend** (merge): COUNT/SUM складываются;
   AVG нельзя усреднять «в лоб» — нужны sum и count с каждого шарда.
3. **Время выполнения** = max(время на шардах, параллельно) + merge; с ростом N
   латентность одного шарда не растёт, но растёт работа по merge и число
   соединений.

## Часть 4. JOIN между шардами

Реальный JOIN сервиса — `AdoptionRepository.GetDetailedByUserIdAsync`
(`JOIN adoptions + animals + users + shelters`). После шардирования
`adoptions` лежит на шардах, а справочники — на Primary лаб 1–4.
Фактический прогон (user_id = 42 → shard1):

```text
1) shard1: SELECT ... FROM adoptions WHERE user_id = 42
   -> animal_id = [18, 354, 261, 261, 43]
2) Primary: SELECT id, name FROM animals WHERE id IN (18, 43, 261, 354)
3) merge в backend -> DTO
```

Ответы:
1. **Если связанные записи на разных шардах** — обычный SQL-движок их не
   увидит: межсерверного JOIN в PostgreSQL не существует.
2. **Обычным SQL к одному PostgreSQL — нельзя** (кроме случая co-location,
   когда обе таблицы лежат на одном шарде).
3. **Передавать пришлось бы** либо все заявки пользователя на узел со
   справочником, либо весь справочник животных на каждый шард.
4. **Выбор shard key для локального JOIN:** шаршировать `animals` по тому же
   ключу, что и `adoptions` (владелец заявки). Тогда JOIN «заявка + животное»
   чаще выполняется внутри одного шарда; но JOIN «заявки + все животные
   приюта» остаётся распределённым — животное может быть в заявке другого
   пользователя.

## Часть 5. ORDER BY + LIMIT

Аналог `AnimalRepository.GetPagedAsync` (`ORDER BY created_at DESC LIMIT N`).
Фактический прогон (LIMIT 10 на каждом шарде):

```text
shard0: top-10, старейшая строка выборки = 2026-09-17 09:49:00
shard1: top-10, старейшая строка выборка = 2026-09-17 04:16:00
shard2: top-10, старейшая строка выборки = 2026-09-17 06:58:00
merge -> глобальный top-10, первые 3:
   id=30 965 (11:54), id=75 840 (11:44), id=67 834 (11:30)
```

**Почему недостаточно одного шарда:** самые свежие записи находятся на разных
шардах (старейшие строки локальных top-10 различаются на ~5 часов) — топ
только с одного шарда пропустил бы более свежие строки других. Merge требует
**top-N с каждого шарда**; при LIMIT < N на шарде глобальный ответ может
оказаться неполным.

## Часть 6. Отказ одного шарда

Живой тест: `docker stop shelter_shard2` → проверки → `docker start`
(контейнер возвращён в состояние healthy).

```text
- shard2: недоступен — connection to server at "localhost", port 5447 failed
- shard0: запросы работают (33 802 строк)
```

1. **Недоступные данные:** все заявки пользователей, маршрутизируемых на
   shard 2 — ~1/3 всех `adoptions`.
2. **Неработающие endpoint'ы:** `GET/POST/PUT/DELETE /api/adoptions` этих
   пользователей, `GET /api/users/{id}/adoptions` для них; глобальные
   агрегаты (`/api/adoptions/stats/by-status`) становятся неполными.
3. **Остальной сервис работает:** shard 0 и 1 (≈2/3 пользователей),
   справочники на Primary, чтение животных.
4. **Backend при обращении к недоступному шарду:** таймауты подключения,
   понятная клиенту ошибка 503 (не 500-ка всего сервиса), ретраи только
   идемпотентных чтений, healthcheck шардов, частичная деградация.
5. **Повышение отказоустойчивости:** реплика каждого шарда + автоматический
   failover, бэкапы per-shard, буферизация записей (outbox-очередь),
   режим read-only при отказе записи.

## Часть 7. Hot Shard

Модель нагрузки: по одному чтению ленты на каждую запись + три «кита»
(user_id 7, 42, 1337 — по 300 000 опросов своего профиля):

| Шард | Строк | Доля строк | Запросов (модель) | Доля запросов |
|------|------:|-----------:|------------------:|--------------:|
| shard0 | 33 802 | 33.80% | 333 802 | 33.38% |
| shard1 | 33 592 | 33.59% | 633 592 | **63.36%** |
| shard2 | 32 606 | 32.61% | 32 606 | **3.26%** |

**Возможные причины:** популярный пользователь (на shard1 «киты» 42 и 1337),
тип запросов (лента опрашивается чаще, чем создаются заявки), неудачный
shard key. **Равное число строк не означает равную нагрузку:** запросы идут
по shard key, а активность ключей различается на порядки. Лечение: кэш
горячих ключей (Redis уже в стеке сервиса), перенос части дуг кольца,
реплика горячего шарда, составной shard key.


## Часть 8. Итоговый анализ shard key

**Подходит ли `user_id` как shard key для `adoptions`? — Да, подходит,
с оговорками.**

**Плюсы**
- Ключ известен до INSERT — запись сразу попадает на нужный шард.
- `GET /api/users/{id}/adoptions`, INSERT/UPDATE/DELETE заявки — single-shard,
  работают с локальным индексом.
- user_id никогда не меняется — записям не требуется переезд.
- Распределение близко к равномерному (max/min = 1.037 на 100 000 записей).

**Минусы — что становится распределённым**
- Глобальная статистика (`GET /api/adoptions/stats/by-status`) — merge по всем
  шардам.
- `GET /api/animals/{id}/adoptions` (заявки по животному) — животное не связано
  с ключом, приходится опрашивать все шарды.
- JOIN со справочниками (animals/users/shelters на Primary) — два запроса + merge.

**Самые сложные операции**
- **JOIN** — распределённый почти всегда (справочники на Primary).
- **aggregation** — нужен merge; AVG требует sum+count, а не усреднения.
- **ORDER BY** — top-N с каждого шарда + merge; глубокая пагинация дорога.
- **migration** (3→4) — modulo 76% / кольцо 28% перемещений (лаба 5).
- **backup** — только per-shard, плюс согласованность между шардами.
- **восстановление** — восстановленный шард может отстать от остальных.
- **балансировка** — «киты» не делятся хешем; нужен перенос дуг/ключей.

**Вывод:** если бы проектировал систему заново — оставил бы `user_id`,
но с Consistent Hashing и vnode'ами (вместо modulo), репликой на каждый шард
и кэшем горячих ключей. Альтернативный кандидат — составной ключ
`(shelter_id, user_id)` для co-location заявок с животными приюта, но он
переносит перекос с пользователей на приюты (крупный приют = hot shard),
поэтому для сервиса заявок ключ по пользователю остаётся лучшим выбором.
