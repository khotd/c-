## Задание 11. Когда индекс не спасает

Запрос `GROUP BY DATE(created_at)` за 365 дней на ~100M строк:

1. Даже с индексом по `created_at` нужно обработать огромный объём строк года.  
2. По сути почти вся «горячая» таблица + HashAggregate по дням.  
3. Индекс не отменяет агрегацию.  
4. Дальше: партиционирование по дате, rollup/MV, архивация, OLAP.

Сильнее всего от роста зависит **Q2 — диапазон дат без узкого ключа** (30 дней): на 5M без индекса ~**484 ms**, с индексом по `created_at` всё ещё ~**98 ms**.

### Задание 18. Улучшение

1. Индекс `(user_id, created_at DESC)` — для списков пользователя.

### Задание 19. Граница применимости (по измерениям)

При объёме около **1–5 млн** записей запрос по диапазону дат (Q2) занимает **десятки–сотни мс** даже с индексом; точечный `user_id` индексом спасается (~1 ms), но аналитика/широкий range — нет.  
**Индексов становится недостаточно**, когда запрос обязан прочитать большую долю растущей таблицы — нужен следующий уровень (partitioning / предагрегация).
