# Лабораторная работа №2
# Рост данных и пределы индексов

Проект: Animal Shelter (`project/`).  
Экспериментальная БД: схема `lab2`, таблица `events` (рост **10k → 100k → 1M → 5M**).  
Сырые логи: `TASK/02_growth_performance/results/`.  

**Цель:** показать, как меняются размер данных, планы и время запросов при росте таблицы; где индекс ещё спасает, а где уже нужен следующий уровень (партиционирование).

---

## Часть A. Тестовая таблица `lab2.events`

### Задания 1–2. Подготовка

Создана схема `lab2` и таблица событий:

```sql
CREATE SCHEMA IF NOT EXISTS lab2;
CREATE TABLE lab2.events (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL,
    event_type VARCHAR(50) NOT NULL,
    payload JSONB,
    created_at TIMESTAMP NOT NULL
);
```

Данные наращивались контрольными точками: **10 000 → 100 000 → 1 000 000 → 5 000 000** строк.

### Задание 3. Рост размера таблицы

| Объём | Table size | Total (с индексами позже) |
|-------|------------|---------------------------|
| 10k | **672 kB** | 944 kB |
| 100k | **6.7 MB** | 8.9 MB |
| 1M | **65 MB** | 87 MB |
| 5M | **326 MB** | 433 MB (до доп. индексов) |

Логи: `measure_{10k,100k,1m,5m}_noindex.log`.

**Вывод:** размер растёт примерно линейно с числом строк. После добавления индексов на 5M суммарный объём заметно больше (индексы занимают сотни МБ).

### Задание 4. SELECT без индекса при росте

Запрос: `SELECT * FROM lab2.events WHERE user_id = 123;`

| Объём | План | Execution Time |
|-------|------|----------------|
| 100k | Seq Scan | **~6.3 ms** |
| 1M | Seq / Parallel Seq | **~31 ms** |
| 5M | Parallel Seq Scan | **~105–161 ms** |

**Вывод:** без индекса время точечного поиска растёт вместе с таблицей (почти линейно).

### Задание 5. Тот же запрос с индексом на 100k / 1M / 5M

Индекс: `CREATE INDEX idx_events_user_id ON lab2.events(user_id);`

| Объём | Без индекса | С индексом | Ускорение |
|-------|-------------|------------|-----------|
| 100 000 | **6.3 ms** | **0.15 ms** | ~42× |
| 1 000 000 | **31.4 ms** | **0.19 ms** | ~167× |
| 5 000 000 | **160.8 ms** | **0.36 ms** | ~445× |

Логи: `gap_{100k,1m,5m}_{noindex|withindex}.log`.

**Вывод:** разница заметна уже на **100k**, критична на **1M+**. Чем больше таблица, тем сильнее относительный выигрыш точечного индекса.

### Задание 6. Range по `created_at`

Запрос (пример): `WHERE created_at >= NOW() - INTERVAL '1 day'`

| Объём 5M | Без индекса | С `idx_events_created_at` |
|----------|-------------|---------------------------|
| 1 день | ~**422 ms** Parallel Seq | ~**63 ms** Bitmap Index Scan |

Широкий диапазон всё равно читает много строк — индекс помогает, но не делает запрос «мгновенным».

### Задание 7. ORDER BY + LIMIT

```sql
SELECT * FROM lab2.events
WHERE user_id = 123
ORDER BY created_at DESC
LIMIT 100;
```

| 5M | Без индекса | С `(user_id, created_at DESC)` |
|----|-------------|-------------------------------|
| Время | ~**113 ms** (Seq + Sort) | ~**0.3 ms** |

Составной индекс под фильтр + порядок делает пагинацию дешёвой.

### Задание 8. Агрегация

```sql
SELECT event_type, COUNT(*)
FROM lab2.events
WHERE created_at >= NOW() - INTERVAL '30 days'
GROUP BY event_type;
```

На 5M: без индекса ~**326 ms**; с индексом по дате ~**184 ms** — всё ещё тяжело (много строк + HashAggregate).

**Вывод:** индекс сужает вход, но **не отменяет** агрегацию большого объёма.

### Задание 9. Цена INSERT при наличии индексов

Вставка **100 000** строк:

| Сценарий | Время |
|----------|-------|
| Без доп. индексов | **284 ms** |
| С 3 индексами (`user_id`, `created_at`, составной) | **830 ms** |

Запись замедлилась ~**2.9×**.

Логи: `insert_100k_no_indexes.log`, `insert_100k_with_indexes.log`.

### Задание 10. Размеры индексов (на ~5M)

| Индекс | Размер |
|--------|--------|
| `events_pkey` | 109 MB |
| `idx_events_user_id` | 34 MB |
| `idx_events_created_at` | 108 MB |
| `idx_events_user_created` | 151 MB |

Лог: `gap_index_sizes_5m.log`.

**Вывод:** индексы сопоставимы по размеру с таблицей — «индексировать всё» дорого по диску и по записи.

### Задание 11. Когда индекс не спасает

Запрос вида:

```sql
SELECT DATE(created_at), COUNT(*)
FROM events
WHERE created_at >= NOW() - INTERVAL '365 days'
GROUP BY DATE(created_at);
```

на очень большом объёме (ориентир ~100M):

1. Даже с индексом по `created_at` за год нужно обработать огромную долю «живой» таблицы.  
2. Далее — HashAggregate по дням: CPU + I/O.  
3. Индекс не делает агрегацию бесплатной.  
4. Дальше: **партиционирование**, rollup / материализованные представления, архивация, OLAP.

## Часть B. Сущность проекта `adoptions`

### Scaling Entity

**Таблица:** `adoptions` (стенд роста: `lab2.adoptions_growth`; живая таблица доведена до **~5 000 000** строк).

Почему растёт быстрее остальных: каждое действие пользователя — новая запись; животных/приютов мало, усыновлений — поток.

Поля фильтрации: `user_id`, `status`, `created_at`, `animal_id`.

### Задания 12–16. Три рабочих запроса на 100k / 1M / 5M

Контролируемый стенд `lab2.adoptions_growth` (те же запросы, что у сервиса).

**Q1** — точечный поиск:
```sql
SELECT * FROM adoptions WHERE user_id = 2;
```

**Q2** — диапазон дат (узкое место):
```sql
SELECT * FROM adoptions
WHERE created_at >= NOW() - INTERVAL '30 days'
  AND created_at < NOW();
```

**Q3** — список пользователя с пагинацией:
```sql
SELECT * FROM adoptions
WHERE user_id = 2
ORDER BY created_at DESC
LIMIT 50;
```

| Объём | Q1 no / yes | Q2 no / yes | Q3 no / yes |
|-------|-------------|-------------|-------------|
| 100k | 6.0 / **0.21** ms | 20.5 / **0.98** ms | 5.9 / **0.12** ms |
| 1M | 31.4 / **0.96** ms | 117 / **10.4** ms | 32.1 / **0.07** ms |
| 5M | 115.5 / **7.5** ms | **484** / **98** ms | 125.8 / **0.14** ms |

Логи: `project_growth_{100k,1m,5m}_{noindex|withindex}.log`.

### Задание 17. Узкое место

Сильнее всего от роста зависит **Q2 — диапазон дат** без узкого равенства по пользователю:  
на 5M без индекса ~**484 ms**, с индексом по `created_at` всё ещё ~**98 ms**.

Q3 с `user_id + LIMIT` и составным индексом остаётся **субмиллисекундным**.

### Задание 18. Что улучшить

1. Индекс `(user_id, created_at DESC)` — списки пользователя.  
2. Индекс `(created_at)` — диапазоны.  
3. **Партиционирование по `created_at`** (лабораторная №3) — prune месяца вместо скана всей истории.

В проекте составные индексы уже добавлены (лаба 1 / Liquibase `012-...`); партиции — лаба 3.

### Задание 19. Граница применимости индексов

При объёме **~1–5 млн** записей:

- точечный `user_id` индексом спасается (~1 ms и меньше);  
- range по датам занимает **десятки–сотни мс** даже с индексом;  
- агрегации / широкий SELECT по большой доле таблицы — индексов недостаточно.

**Формулировка:** индексов становится мало, когда запрос обязан прочитать большую долю растущей таблицы — нужен partitioning / предагрегация.

---

## Выводы

1. Без индекса время поиска растёт вместе с таблицей.  
2. Точечный индекс даёт ускорение на порядки (особенно на 1M–5M).  
3. Много индексов замедляют INSERT (~3× в эксперименте).  
4. Range и GROUP BY на большом окне остаются дорогими.  
5. На сущности `adoptions` узкое место — диапазон дат → переход к **лабе 3 (partitioning)**.
