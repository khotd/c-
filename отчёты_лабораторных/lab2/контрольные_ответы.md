# Контрольные вопросы и ответы — Лаба 2
## Когда индексов недостаточно / рост данных

1. **Почему Seq Scan не всегда плохой план?**  
   Если запрос читает большую долю таблицы, последовательное чтение страниц дешевле множества случайных переходов по индексу к разным местам heap.

2. **Почему PostgreSQL может не использовать существующий индекс?**  
   Низкая селективность; устаревшая статистика; выражение в WHERE не совпадает с ключом индекса; Index Scan по оценке дороже Seq Scan; условие не по ведущей колонке составного индекса (leftmost prefix).

3. **Что происходит с индексом при INSERT?**  
   Для каждой новой строки значение ключа добавляется в структуру индекса (B-Tree и др.). Это дополнительный I/O и CPU сверх записи в саму таблицу.

4. **Почему много индексов замедляет запись?**  
   Каждый INSERT/UPDATE/DELETE должен обновить все затронутые индексы. Чем их больше, тем дороже изменение данных.

5. **Что такое селективность?**  
   Доля строк таблицы, удовлетворяющих условию фильтрации.

6. **Почему индекс хорош для небольшой части таблицы?**  
   По индексу находится мало TID, мало обращений к heap — выигрыш против полного скана большой.

7. **Почему индекс менее полезен, если возвращается большая часть таблицы?**  
   Много случайных чтений по куче обычно дороже одного последовательного Seq Scan.

8. **Зачем нужен EXPLAIN ANALYZE?**  
   Чтобы увидеть реальный план и фактическое время выполнения, а не только оценку планировщика (cost).

9. **Что значит Rows Removed by Filter?**  
   Сколько строк было прочитано при доступе к данным, а потом отброшено фильтром (условие применилось уже после Scan, а не через Index Cond).

10. **Что значит Index Cond?**  
    Условие, которое применил сам индекс при поиске по ключу. Это эффективнее, чем Filter после чтения лишних строк.

11. **Чем Index Scan отличается от Bitmap Index Scan?**  
    **Index Scan** обычно идёт по индексу и сразу (или по ходу) читает строки.  
    **Bitmap Index Scan** сначала собирает bitmap TID, затем **Bitmap Heap Scan** читает страницы таблицы пачками — выгоднее при большем числе попаданий.

12. **Почему важен порядок колонок в составном индексе?**  
    Работает правило leftmost prefix: индекс `(user_id, created_at)` помогает по `user_id` и по `user_id + created_at`, но не по одному только `created_at`.

13. **Почему GROUP BY может оставаться дорогим при индексе?**  
    Индекс может сузить набор строк, но каждую подходящую строку всё равно нужно агрегировать. На миллионах строк HashAggregate/GroupAggregate остаются тяжёлыми.

14. **Как статистика влияет на план?**  
    Планировщик оценивает число строк и стоимость по статистике (`pg_statistic`). Устаревшая статистика → неверный план (например, Seq вместо Index). Обновление: `ANALYZE`.

15. **Что происходит с производительностью при росте таблицы?**  
    Seq Scan дорожает почти линейно. Даже Index Scan может чуть замедляться (высота B-Tree, размер индексов, I/O). Больше всего страдают широкие диапазоны и агрегации — читается всё больше данных.

16. **Почему нельзя индексировать все колонки?**  
    Занимают место на диске, замедляют запись, усложняют обслуживание; часть индексов никогда не окупится запросами.

17. **Как узнать размер таблицы?**  
    ```sql
    SELECT pg_size_pretty(pg_relation_size('lab2.events'));           -- только таблица
    SELECT pg_size_pretty(pg_total_relation_size('lab2.events'));    -- таблица + индексы
    ```

18. **Как узнать размер индекса?**  
    ```sql
    SELECT pg_size_pretty(pg_relation_size('idx_events_user_id'));
    -- или из pg_stat_user_indexes:
    SELECT indexrelname, pg_size_pretty(pg_relation_size(indexrelid))
    FROM pg_stat_user_indexes
    WHERE schemaname = 'lab2';
    ```

## Краткий вывод по измерениям (к защите)

### Part A — `events`, `WHERE user_id = 123`

| Объём | Без индекса | С индексом |
|-------|-------------|------------|
| 100k | 6.3 ms | 0.15 ms |
| 1M | 31.4 ms | 0.19 ms |
| 5M | 160.8 ms | 0.36 ms |

INSERT 100k строк: **284 ms** без доп. индексов → **830 ms** с тремя индексами (~2.9× медленнее).

### Part B — `adoptions`

Узкое место — range по `created_at` за 30 дней на 5M: **~484 ms** без индекса / **~98 ms** с индексом.  
`user_id + LIMIT 50` с составным индексом остаётся **~0.1 ms**.

**Итог:** при ~5 млн записей широкий диапазон дат занимает порядка **0.1–0.5 с**; индекс помогает, но не решает проблему роста навсегда — нужен следующий уровень (**партиционирование**, лаба 3).
