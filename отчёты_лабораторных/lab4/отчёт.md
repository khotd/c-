# Лабораторная работа №4
# Масштабирование чтения PostgreSQL: Primary + Replica

Проект: Animal Shelter (`project/`).  
Сырые проверки: `TASK/04_read_scaling/results/`.

**Цель:** настроить streaming replication и Read Scaling — запись на Primary, часть чтений на Replica; понять WAL и replication lag.

---

## Часть 1. Primary и Replica в Docker

Фрагмент `project/docker-compose.yml`:

| Контейнер | Роль | Порт (хост) |
|-----------|------|-------------|
| `animal-shelter-db` (`db`) | **Primary** | `5432` |
| `animal-shelter-db-replica` (`db-replica`) | **Replica** (hot standby) | `5433` |
| `animal-shelter-db-repl-setup` | one-shot: роль `replicator` + `pg_hba` | — |

Подключение:

```text
Primary:  Host=localhost Port=5432  DB=projectDB  User/Pass=project/project
Replica:  Host=localhost Port=5433  DB=projectDB  User/Pass=project/project
```

Из контейнеров приложения: Host `db` / `db-replica`, порт `5432`.

Primary запускается с `wal_level=replica`, `max_wal_senders`, `hot_standby`.  
Replica поднимается через `pg_basebackup -R` (создаёт `standby.signal` и `primary_conninfo`).

## Часть 2. Streaming replication

Цепочка:

1. Приложение / SQL меняет данные на **Primary**  
2. Изменение пишется в **WAL**  
3. **Replica** получает поток WAL (`walreceiver`)  
4. Replica **воспроизводит** (replay) изменения  

Проверка на Primary:

```sql
SELECT client_addr, state, sync_state, replay_lag
FROM pg_stat_replication;
```

Фактический результат (прогон лабы):

```text
client_addr | state     | sync_state | replay_lag
172.22.0.6  | streaming | async      | ~3 ms
```

Режим **async** — нормален для учебного Read Scaling.

## Часть 3. Доказательство репликации

На Primary:

```sql
INSERT INTO shelters (name, ...) VALUES ('lab4_repl_…', ...) RETURNING id, name;
-- id=3, name=lab4_repl_b0a4f4bb
```

На Replica через ~1–2 с:

```sql
SELECT id, name FROM shelters WHERE name = 'lab4_repl_b0a4f4bb';
-- та же строка найдена
```

Лог: `results/01_replication_ok.log`.

## Часть 4. Read-only поведение Replica

```sql
-- на Replica:
INSERT INTO shelters (...) VALUES (...);
-- ERROR: cannot execute INSERT in a read-only transaction
```

**Вывод:** Replica — не независимая БД для записи. Запись только на Primary, иначе рассинхрон копий.

## Часть 5. Чтение сервиса с Replica

Конфигурация:

```yaml
# docker-compose web environment
ConnectionStrings__DefaultConnection=Host=db;...
ConnectionStrings__ReplicaConnection=Host=db-replica;...
```

Код: `Repositories/AnimalRepository.cs` — поле `_readConnectionString` из `ReplicaConnection`.

| Операция | Куда |
|----------|------|
| `GET /api/animals` (GetPaged) | **Replica** |
| `GET /api/animals/with-shelter` | **Replica** |
| `GetAllAsync` | **Replica** |
| INSERT/UPDATE/DELETE животных | **Primary** (`DefaultConnection` / `AppDbContext`) |

Так реализован один реальный read-сценарий backend (каталог/список животных).

## Часть 6. Replication lag

После INSERT на Primary сразу SELECT на Replica обычно уже видит строку (лаг миллисекунды).  
В `pg_stat_replication.replay_lag` зафиксировано порядка **~3 ms**.

**Главный вывод:** репликация ≠ мгновенная синхронизация. Между commit на Primary и replay на Replica есть задержка — **replication lag**. Поэтому SELECT сразу после INSERT через Replica теоретически может вернуть «старое» состояние (особенно при нагрузке/сети).

---

## Выводы

1. Primary пишет, Replica читает и догоняет по WAL.  
2. Streaming replication работает (`state=streaming`).  
3. Запись на Replica запрещена.  
4. Read Scaling разгружает Primary по чтениям, не заменяя индексы/оптимизацию SQL.  
5. Async Replica допускает краткий lag — это ожидаемо.
