# Контрольные вопросы и ответы — Лаба 3
## Партиционирование PostgreSQL

1. **Что такое partitioning?**  
   Разделение одной логической таблицы на несколько физических частей (партиций) по ключу, при этом для приложения таблица остаётся одной (`adoptions`).

2. **Чем partitioning отличается от индекса?**  
   Индекс ускоряет поиск строк внутри таблицы/партиции. Партиционирование уменьшает объём данных, которые нужно рассматривать (prune), и упрощает удаление/архивацию старых данных (`DROP PARTITION`). Решают разные задачи, часто используются вместе.

3. **Какие стратегии поддерживает PostgreSQL?**  
   RANGE, LIST, HASH (declarative partitioning).

4. **Когда использовать RANGE?**  
   Когда данные естественно делятся по диапазону (даты, числа), запросы часто фильтруют по диапазону, нужно удалять старые периоды целиком.

5. **Когда использовать LIST?**  
   Когда есть конечный набор категорий (тип клиента, страна, статус) и запросы часто фильтруют по категории.

6. **Когда использовать HASH?**  
   Когда нужно равномерно распределить данные/нагрузку без естественного диапазона (например, по `user_id`).

7. **Как выбрать partition key?**  
   По полю, которое часто в WHERE, по которому данные растут и архивируются; ключ должен входить в PRIMARY KEY / UNIQUE.

8. **Что такое partition pruning?**  
   Исключение ненужных партиций из плана запроса, если по условию WHERE понятно, какие сегменты не нужны.

9. **Почему pruning может не сработать?**  
   Фильтр не по ключу партиционирования; функция/нестабильное выражение над ключом; параметр мешает константному pruning.

10. **Можно ли использовать индексы вместе с partitioning?**  
    Да. Индексы на parent/партициях + pruning часто дают лучший результат, чем только индекс или только партиции.

11. **Что будет, если подходящей партиции нет?**  
    INSERT завершится ошибкой (если нет DEFAULT-партиции). Поэтому будущие партиции создают заранее.

12. **Зачем создавать будущие партиции заранее?**  
    Чтобы INSERT не ломались, когда наступает новый месяц/день/период.

13. **Почему создание партиций должно быть автоматизировано?**  
    Вручную легко забыть. Job идемпотентно поддерживает горизонт вперёд.

    **В нашем проекте:** не cron, а `BackgroundService` (`PartitionMaintenanceHostedService`) раз в час + ручной API.

14. **Чем логирование ошибки отличается от alerting?**  
    Лог можно не заметить. Alert активно уведомляет (файл/email/мессенджер).

15. **Что такое recovery alert?**  
    Уведомление, что проблема устранена (переход CRITICAL → OK).

16. **Почему нельзя бесконечно слать одинаковый alert?**  
    Алерт-шторм. Нужна дедупликация: повторно слать при смене статуса / recovery, а не на каждой проверке.

17. **Всегда ли partitioning ускоряет запросы?**  
    Нет. Без фильтра по ключу обходятся все партиции. Слишком мелкие или слишком крупные партиции тоже вредят.

18. **Проблемы при неправильном размере партиций?**  
    Слишком мелкие — overhead планирования и метаданных. Слишком крупные — слабый prune и тяжёлое обслуживание.

## Стратегии (часть 7)

| Сценарий | Стратегия |
|----------|-----------|
| A события + удаление старше 3 лет | RANGE по дате |
| B B2C/B2B/Enterprise | LIST |
| C равномерно по user_id | HASH |
| D аналитика по created_at BETWEEN | RANGE по дате |
| E платежи по странам | LIST |

## Границы RANGE

- `TO` не включает нижнюю границу следующей партиции: `[FROM, TO)`.  
- Нет партиции под дату → INSERT ERROR (без DEFAULT).
