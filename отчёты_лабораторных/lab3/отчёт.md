# Лабораторная работа №3
# Партиционирование PostgreSQL

Проект: Animal Shelter (`project/`).  
Учебная схема: `lab3` (RANGE / LIST / HASH).  
Сущность проекта: **`adoptions`**, ключ **`created_at`**, стратегия **RANGE по месяцам**.  
Сырые логи: `TASK/03_partitioning/results/`.

**Цель:** разделить большую растущую таблицу на партиции, добиться partition pruning, автоматизировать создание/удаление партиций и alerting при сбоях.

**Автоматизация** Используется Declarative partitioning PostgreSQL.

## Часть A. Учебные эксперименты (`lab3`)

### Стратегии

| Стратегия | Когда | Пример |
|-----------|--------|--------|
| **RANGE** | даты/числа, удаление старых периодов, фильтр BETWEEN | события по дням/месяцам |
| **LIST** | конечный набор категорий | тип клиента, страна |
| **HASH** | равномерное распределение без естественного диапазона | по `user_id` |

### Границы RANGE (полуинтервал `[FROM, TO)`)

| Значение `created_at` | Партиция |
|----------------------|----------|
| `2026-09-10 12:00:00` | `events_2026_09_10` |
| `2026-09-11 00:00:00` | `events_2026_09_11` |
| `2026-09-12` без партиции / без DEFAULT | **ERROR** при INSERT |

### Partition pruning

- Фильтр по ключу партиционирования → в плане остаются нужные партиции.  
- Фильтр не по ключу (например, только `event_type`) → обход всех партиций.  
- **DEFAULT**-партиция ловит «прочее», но может превратиться в свалку.

### Индексы + partitioning

Индексы создаются на parent и действуют локально на партициях. Pruning + Index Scan / Index Only Scan часто лучше, чем одно из двух.

Логи: `results/01_experiments.log`.

## Часть B. Партиционирование `adoptions` в проекте

### Решение

| Параметр | Значение |
|----------|----------|
| Таблица | `adoptions` |
| Ключ | `created_at` |
| Стратегия | RANGE, месяц |
| Почему | поток усыновлений растёт; запросы с датами; удобный DROP старых месяцев |
| Миграция | Liquibase `013-ensure-adoption-partitions.sql` + SQL `02_partition_adoptions.sql` |

PK после partitioning: составной `(id, created_at)` (ключ партиционирования должен входить в UNIQUE/PK).

### Три API-подобных запроса (pruning)

#### 1) Диапазон дат — pruning ЕСТЬ

```sql
SELECT * FROM adoptions
WHERE created_at >= '2026-03-01' AND created_at < '2026-04-01'
ORDER BY created_at DESC LIMIT 50;
```

В плане читается в основном **`adoptions_2026_03`** (~10 ms). Остальные месяцы отсекаются.

#### 2) GET по `id` — pruning слабый / нет

```sql
SELECT * FROM adoptions WHERE id = 1000;
```

Ключ партиции — дата, не `id` → обход всех партиций (~1.6 ms на демо-объёме). Partitioning не ускоряет lookup только по id.

#### 3) `GROUP BY status` без даты — pruning НЕТ

```sql
SELECT status, COUNT(*) FROM adoptions GROUP BY status;
```

Нужны все партиции (~60 ms). С окном по `created_at` pruning помогает (читаются только нужные месяцы).

Лог: `results/03_api_explain_pruning.log`. Подробный разбор: [`отчёт_анализ.md`](отчёт_анализ.md).

### Жизненный цикл партиций

| Операция | Как |
|----------|-----|
| Создание горизонта | `CreatePartitionsJob` — текущий месяц + N вперёд (по умолчанию 3) |
| Удаление старых | `DropOldPartitionsAsync` — DROP старше retention **24 месяца** (кроме `adoptions_default`) |
| Расписание | **не cron** — `BackgroundService` каждые **1 час** |
| Ручной запуск | `POST /api/partitions/create-missing`, `GET /api/partitions/health` |
| Код | `project/Services/Partitioning/PartitionServices.cs` |
| API | `PartitionsController` |

Без заранее созданной партиции INSERT в новый месяц падает с ошибкой (если нет DEFAULT) — поэтому горизонт создают заранее и автоматически.

### Alerting

- **PartitionHealthCheck** проверяет наличие нужных партиций.  
- При отсутствии → статус **CRITICAL** + уведомление (файл в `project/alerts/`, опционально email).  
- После восстановления → **recovery alert** (CRITICAL → OK).  
- Одинаковый CRITICAL не спамится бесконечно (дедупликация до смены статуса).

Сценарий проверки: DROP будущей партиции → CRITICAL → создать снова → OK.  
Демо: `sql/demo_alert_recovery.py`, `sql/04_drop_old_demo.sql`.

## Выводы

1. Partitioning ≠ индекс: индекс ищет строки внутри данных; партиции **отсекают** ненужные куски и упрощают удаление старого.  
2. Для `adoptions` выбран **RANGE по месяцам** на `created_at`.  
3. Pruning работает при фильтре по ключу; без него выигрыша нет.  
4. Создание партиций **автоматизировано через BackgroundService**, не через системный cron; job идемпотентен.  
5. Нужны health-check и alerting, иначе пропущенная партиция ломает INSERT незаметно для логов alone.
