# Индексы и EXPLAIN ANALYZE

## Часть 1. Работа с тестовой базой

Чистый baseline (таблица без доп. индексов) переснят: `TASK/01_indexes_explain/results/04_clean_baseline.log`.  

### Задания 1–2. Подготовка

Создана схема `lab1`, таблица `orders`, загружено **1 000 000** строк, выполнен `ANALYZE`.

### Задание 3. EXPLAIN

Запрос: `SELECT * FROM lab1.orders WHERE user_id = 123;`

**До индексов:** Parallel Seq Scan (Filter `user_id = 123`).  
Планировщик оценивает малое число строк, но всё равно читает таблицу целиком через воркеры.

### Задание 4. EXPLAIN ANALYZE

| Метрика | До индекса (clean) | После `idx_orders_user_id` |
|---------|---------------------|----------------------------|
| Scan | Parallel Seq Scan | Bitmap Index Scan → Bitmap Heap Scan |
| actual rows | 11 (в clean-прогоне) / ранее 4 | 11 |
| Rows Removed by Filter | ~333k на воркер | — (Index Cond) |
| Execution Time | **~35 ms** | **~0.15 ms** |

1. EXPLAIN — только план; EXPLAIN ANALYZE — реальное выполнение.  
2. ANALYZE дольше, т.к. делает работу запроса.  
3. estimated ≠ actual при устаревшей/неточной статистике.

### Задание 5. Sequential Scan

- `SELECT * FROM orders` / `amount > 0` → Seq Scan оправдан (нужна почти вся таблица).  
**Вывод:** Seq Scan лучше индекса, когда доля результата велика или таблица мала.

### Задание 6. Первый индекс

| Метрика | До | После |
|---------|----|-------|
| Тип Scan | Parallel Seq Scan | Bitmap Index/Heap Scan |
| Execution Time | ~35 ms | **~0.15 ms** |
| Индекс | — | `idx_orders_user_id` |

### Задание 7–8. Низкая селективность / распределение

`status` ≈ 25% на значение. До индекса: Seq Scan ~112 ms на `status='PAID'`.  
С индексом — Bitmap Index Scan, но выигрыш умеренный при такой доле строк.  
**Вывод:** низкая селективность → индекс менее полезен.

### Задание 9–10. Range / Bitmap

Узкий диапазон дат → Bitmap Index Scan выгоден; широкий (~год) → Seq Scan.  
`amount BETWEEN` → классический Bitmap Heap + Bitmap Index Scan.

### Задание 11–12. Несколько индексов vs composite

При двух отдельных индексах PostgreSQL часто берёт более селективный (`user_id`) + Filter по `status` (BitmapAnd не всегда появляется — зависит от cost).  
Составной `(user_id, status)` → **Index Scan**, ~0.07 ms — эффективнее для этого запроса.

### Задание 13. Порядок колонок

`(user_id, created_at)` vs `(created_at, user_id)` — разные индексы (leftmost prefix).

### Задание 14–15. ORDER BY / pagination

**До** `(user_id, created_at DESC)`: Parallel Seq Scan + Sort (~48 ms).  
**После:** Index/Bitmap по user + Sort quicksort по ~11 строкам (~0.15 ms).  
Sort **не всегда исчезает** при крошечном результате — in-memory Sort дешев; важно, что исчезло сканирование миллиона строк.  
Для pagination `LIMIT 20` индекс по `(user_id, created_at DESC)` — правильная структура.

### Задание 16. Index Only Scan

С `INCLUDE (id, status, created_at)` планировщик может выбрать Index Only Scan (в ранних прогонах) или Bitmap по covering-индексу — зависит от visibility map / cost. Условие IOS: все нужные колонки в индексе + актуальная VM.

### Задание 17. Partial index

При `NEW` ≈ 25% partial `WHERE status='NEW'` слабо выигрывает у обычного индекса.  
Partial полезен, когда подмножество **маленькое** (например, 1–5% «открытых» заказов).  
Для `ORDER BY created_at LIMIT 100` + partial — Index Scan ~0.46 ms.

### Задание 18. Expression index

`LOWER(email)` не использует индекс по `email` → нужен expression index.

### Задание 19–21

INSERT дорожает с числом индексов; финальный индекс `(user_id, status, created_at DESC)` закрывает равенства + диапазон + порядок.

## Часть 2. Работа со своим сервисом

### Scaling Entity

**Таблица:** `adoptions`

Отвечает за заявки/факты усыновления (animal_id, user_id, status, created_at).

Почему растёт быстрее: каждое обращение пользователя — новая запись; животных и приютов ограниченное число, усыновлений — поток.

Ожидаемый объём через год: сотни тысяч – миллионы записей при активном сервисе.

Поля фильтрации: `user_id`, `animal_id`, `status`, `created_at`.

### Задание 25. Текущие индексы проекта (adoptions / связанные)

| Индекс | Колонки | Какие запросы | Использование |
|--------|---------|---------------|---------------|
| `adoptions_pkey` | id (+ created_at после partitioning) | GET by id | да |
| `idx_adoptions_animal_id` | animal_id | GET /animals/{id}/adoptions | да |
| `idx_adoptions_user_id` | user_id | списки по пользователю | да |
| `idx_adoptions_status` | status | фильтр статуса (низкая селективность) | редко/умеренно |
| `idx_adoptions_user_status_created` | (user_id, status, created_at DESC) | API user adoptions + фильтры | да (целевой) |
| `idx_animals_*` / `idx_users_*` | name/status/email… | поиск животных, login | по нагрузке |

Статистика: `pg_stat_user_indexes` (см. `results/03_project_baseline.log`). `idx_scan = 0` ≠ «удалять сразу».

### Задание 26. Проблемы по запросам

| Запрос | Seq Scan? | Селективность | Индекс | Улучшение |
|--------|-----------|---------------|--------|-----------|
| Q1 `user_id=?` | нет (Bitmap) | высокая | `user_id` / composite | ok |
| Q2 `user_id+status+date` | нет | высокая | до: Filter 79 rows; после: Index Cond | composite ✓ |
| Q3 `user_id ORDER BY LIMIT` | нет | высокая | composite; Sort по десяткам строк | ok; узкое место — range без user |

### Исследуемые запросы

#### Query 1 — по user_id

```sql
SELECT * FROM adoptions WHERE user_id = 2;
```

| | До доп. индекса | После `idx_adoptions_user_status_created` |
|--|-----------------|-------------------------------------------|
| Scan | Bitmap Index Scan (`idx_adoptions_user_id`) | Bitmap Index Scan (composite) |
| Execution Time | ~0.56 ms | ~0.20 ms (list+sort LIMIT) |

#### Query 2 — несколько условий

```sql
SELECT * FROM adoptions
WHERE user_id = 2 AND status = 'Pending'
  AND created_at >= NOW() - INTERVAL '365 days';
```

| | До | После |
|--|----|-------|
| Scan | Bitmap по user_id + **Filter** status/date (79 Rows Removed) | Bitmap Index Scan, условия в **Index Cond** |
| Execution Time | ~0.17 ms | **~0.12 ms** |

#### Query 3 — filter + sort + limit

```sql
SELECT * FROM adoptions WHERE user_id = 2
ORDER BY created_at DESC LIMIT 50;
```

Используется индекс по user; Sort quicksort по найденным ~92 строкам (~0.2 ms).

### Оптимизация (задания 27–28)

Добавлена миграция Liquibase:

`liquibase/changelogs/012-lab1-adoptions-indexes.sql`

```sql
CREATE INDEX idx_adoptions_user_status_created
ON adoptions (user_id, status, created_at DESC);

CREATE INDEX idx_adoptions_created_at ON adoptions (created_at);
```

Порядок колонок: равенства (`user_id`, `status`) → диапазон/сортировка (`created_at DESC`) — под API `GET /api/users/{id}/adoptions` и фильтры по статусу/дате.

### Задание 30. Почему нельзя индексировать всё?

Индексы занимают место на диске, замедляют INSERT/UPDATE/DELETE (каждое изменение обновляет индексы), усложняют VACUUM/maintenance.  
Нужны только под реальные селективные запросы, подтверждённые EXPLAIN ANALYZE.
